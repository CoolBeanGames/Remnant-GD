Player Pickup

Pickup, movement and dynamic prompts

player_pickup.gd keeps F drop/pickup, charged RMB throw, collision snapshots and container hooks. _unhandled_input(event) handles wheel and R only for held rotatable_item objects. _update_held_object(delta) composes the hold marker basis with get_hold_rotation() before smoothing, then calls on_held_transform_updated() when provided. The building reference, placement cancellation and package/query helper APIs were removed.

player_move_controller.gd exports wind_drag: float=3, with wind_velocity/applied_wind: Vector3. apply_wind(direction: Vector3, force: float, maximum_speed: float, delta: float) accumulates capped wind separately from walking. _physics_process subtracts the last applied wind from locomotion before adding current wind, retains gravity and disables floor snapping during upward wind. Gravity and ordinary stepping remain.

object_prompts.get_prompts() returns only its configured prompt_set; recipe fallback is removed. prompt_display has ray/pickup references, label_scene and carrying_prompts. Held-object get_carry_prompts() overrides ordinary carrying; otherwise look-at providers apply. Rotatable props append a live [R] Axis hint. The player/level have no building controller. Raycast debugging is off. Reusable prompt labels, key rebinding and ancestor provider resolution remain supported.

In-world gameplay prompts

Scenes/testing_level.tscn has a tiny CenterContainer/TextureRect crosshair, a reusable Scenes/UI/world_prompts.tscn Node3D, text-only ComboDisplay/PortalStatus, and existing WordMessage/DialoguePlayer captions. Look text appears beside the targeted object. Carry controls follow the held model; B placement controls follow the visible ghost. If there is no placement surface, Cancel stays available beside the hold position. Existing key bindings and editable Data/Prompts resources are unchanged. Raycast debugging remains off.

World lettering is camera-facing, unshaded and outlined, with normal depth testing: it needs no additional lamp and respects world geometry. The look ray still enforces range, enabled state and physical occlusion. Only the current controls are instantiated. Mesh bounds are cached for the current owner, exclude hidden upgrade variants and the ghost direction arrow, and move with the model. Readability scaling is bounded; positioning tries the right, then left, and clamps within the viewport. Up to three controls form one column; larger sets use two columns. There is no bottom prompt row or panel.

Prompt entries and sets

prompt_entry describes a hint independently of UI presentation. prompt_set is an ordered reusable resource holding entries: Array[prompt_entry] = []. Null entries are skipped.

Entry variableDefaultPurpose
text: StringemptyAction wording, e.g. Pull Lever.

Combo UI now draws only white text: multiplier, item count/pending points and countdown, followed by earned total. No background, border or timer bar. The first item is 1.0×; the second is 1.5×; each further item adds 0.5×. The refilled window shrinks from 3 seconds by 0.4 seconds per item to a 0.5-second minimum. When the timer expires, the earned total joins ScoreRewards; it does not instantly change the score by the entire amount.

ScoreRewards awards the first point immediately, then waits 0.5 seconds. Each subsequent point reduces the interval by 0.02 seconds. New payouts extend the active queue without resetting its speed. If the interval reaches zero or below, all remaining queued score is awarded together, and speed resets. Score.wav plays loudly through pooled SFX for each award. Grinding still plays Grind.wav per destroyed item. The score sign updates from the actual counting Blackboard score.

E Empty releases basket items at their current positions with zero velocity/angular velocity. Temporary collision exceptions let them fall through the basket bottom under gravity; no forward/upward force, repositioning or spreading is added. Original collider/freeze settings and item wrappers remain intact. Exceptions clear when items leave beneath or beside the basket, or on basket deletion. Carrying still keeps the basket held after emptying.

Remnant GD Architecture Overview

Godot 4.7

A high-performance modular Godot 4.7 architecture featuring centralized data management, signal-driven flags, dynamic scene/bundle instancing, audio pooling, physical interaction raycasting, and reactive hazard systems.

Engine Version Godot Engine 4.7 Forward+
Physics Engine Jolt Physics (3D)
Graphics API Direct3D 12 (Windows)
Autoload Singletons Blackboard, Flags, SceneManager, Audio, Buildings

Core Architecture Principles

The Remnant-GD codebase is engineered around decoupled, single-responsibility services and components:

  • Decoupled State Management: Systems share references, roots, and runtime objects via the global Blackboard service locator, removing tight dependencies between disparate scene branches.
  • Reactive Flag System: Game states, conditions, and mission progression are observed via Flags and reactive flag resource signals.
  • Dynamic Scene & Bundle Orchestration: Scenes are instanced, attached to parent nodes (or auto-resolved via Blackboard["game_root"]), and grouped into lifecycle bundles through SceneManager.
  • Object Pooling Architecture: High-frequency instances (such as spatial 3D audio players) are pre-allocated and recycled using object_pool (Object_Pool.gd), preventing runtime GC stutter.
  • Decoupled Global Audio: Global spatial and stereo sound playback is dispatched through the Audio autoload (audio_global.gd), automatically acquiring pooled audio_player instances and releasing them on completion.
  • Component-Based Player & Interactivity: The player character is split into isolated controllers: mouse look (player_look_controller.gd), kinematic WASD movement with sprint cadence (player_move_controller.gd), group-filtered targeting (raycaster.gd), and interaction dispatch (player_interact.gd).
  • Proxy Interaction Pattern: Physical colliders forward player interactions up to logic nodes via interact_pass_through.gd, keeping collision shapes modular.
  • Contextual Physics Audio: Physics props (e.g., test_object.tscn) evaluate collision partners using collision_sound_matrix.gd and data-driven collision_sound_entry resources to trigger material-appropriate sounds.

F6 gameplay recorder

# In-game lossless gameplay recording

The current implementation is portable under addons/dev_toolkit; the original Global/script paths are compatibility wrappers. See Data/DEV_TOOLS.md for adapter, resource commands, canonical scripts and API identities.
Press **F6** to start, then **F6** again to stop. A REC indicator appears while active; finishing combines the recorded picture and sound in the background. Recording does not restart the game, pause simulation or silence sound playback. It continues through ordinary pause menus. F6 is ignored while typing an F1 report or a console command.

The tilde console also supports `record start`, `record stop`, `record status` and `record folder` (opens the output directory). Recordings are under `.recordings/<timestamp-id>/recording.mkv` in this project, ignored by Git and Godot; exported games use `user://recordings`. They survive save resets. `recording.json` records size, FPS, duration, repeated frames, sound mix rate and warnings. No recordings are uploaded.

The recorder uses an explicit GameplayRecorder.ffmpeg_path when set; otherwise it searches PATH and its private FFmpeg cache. If FFmpeg is missing on Windows x86_64, F6 / `record start` automatically downloads it, shows setup progress and starts recording once ready. F6 again / `record stop` cancels setup; use the normal start command to retry. No download occurs at application startup or during headless/Movie Maker execution. Audio/video encoding runs on a worker thread; video pixels are read on the rendering thread.

## FFmpeg setup

`auto_download_ffmpeg` defaults to true. Its supported default download is Gyan's release essentials ZIP, linked by [FFmpeg's Windows download page](https://ffmpeg.org/download.html#build-windows). The archive is checked against the publisher's SHA-256 file before extracting the executable into `ffmpeg_cache_directory` (default `user://dev_toolkit/ffmpeg`). This is a private application cache: PATH and installed software are unchanged, and later recordings/launches reuse it.

Set `auto_download_ffmpeg = false` for manual setup. A nonempty `ffmpeg_path` selects a specific executable and disables the automatic fallback; invalid paths report an error. On other platforms, install a build with `libx264rgb` on PATH or select it explicitly. Setup failures report a useful message and leave recording stopped. Game audio is captured only after setup succeeds and recording begins.

The portable `DevFFmpegInstaller` can also be used directly: add it to the scene tree, connect its progress/finished signals and call `start_install()`. It returns an empty String when setup starts, or an immediate error. Completion emits `finished(path, error)`; success has an executable path and empty error. `cancel()` stops network work and cooperatively cancels verification. `cached_executable()` locates an existing verified build. The recorder creates this child lazily on its first setup request.

Installer archive/checksum URLs are exported for a host-selected HTTPS mirror; loopback HTTP is allowed for local development/tests. Both the archive and extracted executable have a 256 MiB default size limit. Requests time out after 600 seconds; executable support checks time out after 10 seconds. Hashing, extraction and FFmpeg support checks run on a worker thread. Only fixed filenames are written, and a completed staging folder is published atomically after the SHA-256 and `libx264rgb` checks. `install.json` retains source URLs, provider information and archive/executable digests alongside available LICENSE/README files. Partial or cancelled setup is removed without replacing an older valid build; startup cache discovery checks the executable digest before reuse.

## Quality and controls

The exact rendered viewport size is used, including Windows scaling; there is no spatial downscaling or chroma subsampling. Video is lossless RGB H.264 (`libx264rgb -crf 0 -preset ultrafast -tune zerolatency -pix_fmt rgb24`) in Matroska; audio is stereo 32-bit float PCM at the actual AudioServer mix rate. This preserves the rendered 8-bit RGB picture and game mix. The test decodes both and compares every original byte. Use an editor/player supporting lossless RGB H.264 and float PCM MKV, or convert a copy for sharing.

Default capture_fps is 60, configurable from 1–120 on the GameplayRecorder autoload; 30 reduces load without changing spatial/pixel quality. No game graphics settings are raised automatically. Captures include the game HUD/debug overlays; they do not include other apps, OS cursor, microphone, or HDR master imagery. Master tap includes mixed SFX, music, vocals, footsteps and child-bus effects/gains. Master gain/mute is applied when draining the samples, since bus effects run before its fader; float mix precision is retained rather than clipping it to speaker limits.

GPU readback and lossless compression still cost performance and disk space. This is not a zero-overhead recorder: an eight-packet queue limits memory. If the game misses a frame slot, the preceding frame repeats so video follows wall-clock time instead of speeding up against sound. The manifest records this count. Sound/start boundaries are quantized to audio blocks/video frame ticks; audio is padded or trimmed at the final tail to match the video duration. It never resizes or switches to lossy encoding to hide load.

Audio overflow, full encoder queue, encoder failure or window resolution change ends the clip and reports the reason. Where possible the partial clip is finalized with its warning. Reduce FPS/resolution if needed. Successful finalization removes intermediate video.mkv/audio.f32; failed finalization retains them for recovery. Use game Exit/window close normally so _exit_tree drains the worker and finalizes. A forced editor Stop/F8, crash or process kill cannot guarantee finalization. The recorder has no connection to save/profile state.

# Scripted developer commands

The console dispatches editable command resources rather than a fixed command switch. ## Add a command

1. Create a GDScript extending `res://addons/dev_toolkit/command.gd`.
2. Override `execute(arguments: Array[String], context: DevToolsContext) -> String`.
3. Create a resource using that script. Set its command prefix, optional aliases, usage, description and enabled checkbox.
4. Add the resource to the console's command catalog. Help text is generated from that catalog.

For example, this is the complete implementation of an editable message command:

```gdscript
extends "res://addons/dev_toolkit/command.gd"
@export var prefix: String = "MESSAGE / "

func execute(arguments: Array[String], context: DevToolsContext) -> String:
    var words := PackedStringArray()
    for argument in arguments:
        words.append(context.parse_name(argument))
    return prefix + " ".join(words)
```

Set the resource's `command` to `message`, `usage` to `message "text"`, and enter `message "hello world"` in the console. Any exported fields on a custom script are editable in its resource. The bundled `commands/echo.gd` and `echo.tres` show the same pattern.

Commands may have multiple words, such as `set flag`. Prefix matching ignores case and chooses the longest matching prefix. Argument values retain their original case and quote characters; use `context.parse_name()` for quoted names/text, or JSON for typed values. Keep prefixes and aliases unique between enabled resources. Disabled resources are excluded from execution/help. Invalid arguments should return a readable usage or error string before changing state.

The handler runs ordinary project-authored GDScript and can call code, create scenes or play audio. Console input is treated as arguments; it is not interpreted as GDScript, a filesystem script or a shell command. Only add trusted scripts to the catalog.

Network, verification, extraction and unsupported-platform errors are shown in the recorder status.

## Add a command resource

Each command is a Resource whose script extends `DevConsoleCommand`. Set its `command` prefix, optional `aliases`, `usage`, `description`, and `enabled` in the Inspector, then put that resource into your catalog's `commands` array. Add or replace commands by editing the catalog; the console itself does not need a new branch.

For example, save this as your own command script:

```gdscript
extends DevConsoleCommand

func execute(arguments: Array[String], context: DevToolsContext) -> String:
    if arguments.size() != 1:
        return 'Usage: greet "name"'
    var recipient := context.parse_name(arguments[0])
    context.adapter.set_blackboard("last greeting", recipient)
    return "Hello, " + recipient
```

Create a Resource using that script and set `command = "greet"`, `usage = 'greet "name"'`, and a description. Add it to a `DevCommandCatalog`. Typing `greet "friend"` now runs that resource's script. Resource scripts are trusted project code: the console does not evaluate arbitrary text as GDScript or shell commands.

Prefixes and aliases ignore case. Matching chooses the longest token prefix, so `weather` and `weather forecast` can coexist. Arguments retain their original quoting; `parse_name()` decodes quoted names. Use `tokenize()` for quoted command text and parse JSON explicitly for values when needed. A handler validates its own argument count/types and returns a String explaining its result or usage. Disabled resources do not execute or appear in generated help. Keep prefixes and aliases unique to avoid ambiguous matches.

The default catalog provides `help`, `set flag`, `set bb`, `set score`, `tp`, `fly`, `noclip`, `record`, `log`, and `echo`. It can be duplicated and edited per project. `context.register_command(resource)` also adds a resource at runtime. `context.execute(text)` is the programmatic dispatch API, and `help_text()` derives documentation from the current resources.

Leaving/reloading Game saves through the level's tree_exiting signal; WorldState's continually updated last snapshot is used once actors have left the tree. Reloading through SaveLoader reads the file again before recreating the level. Game clears SceneManager's registrations on teardown so the next level can register under test_level again.

DELETE SAVE AND EXIT in shared Options disables saving first, removes the save and any interrupted temporary write, then quits. Teardown and window-close saves cannot recreate it. The next launch starts fresh. Normal writes flush a temporary file and atomically replace the final file, leaving only remnant.save after success. Invalid versions/data emit save_failed and do not partially restore state; write/delete errors are reported rather than silently treated as success.

# Player voices and cinematic audio

Dialogue waits for the current line's typewriter/hold and optional voice before fading to the next line. E immediately advances to the next line and stops/releases the previous voice. The default RoomSFX bus keeps voices audible before the first door opening. Empty voiceover is safe.

Wake_Up now lasts 12.8 seconds. The rise keeps its original staged motion; the late look-around is stretched: standing 5.35 s, left 7.25 s, right 10.15 s, centred 12.1 s, handoff 12.8 s. Slide 1 plays at pose time 1.3 and Slide 2 at 3.65, with an optional quiet effort bank using the supplied short jump grunts. All pose cues scale with Duration. Dialogue begins at 4.3 seconds by default, after both rise grunts finish. Edit Slide Sounds/Effort Sounds on Wake_Up; clear either bank for silence.

Jumping plays a random clip from vo__jump_1 through vo__jump_6. Five seconds of continuous grounded movement while sprinting starts vo__out of breath.wav; stopping resets the timer. Continuous sprinting can play another breath after the current clip finishes, but never overlaps it. Death/teardown stop and release it. These banks, thresholds and bus are exported on Player_Move_Controller.

Grinder death first cancels dialogue and heavy breathing, locks movement/look/breathing, plays a random vo__death_1 through vo__death_4 and fades vision to black over 0.65 seconds. It waits until both the fade and death voice finish before rebuilding the room and starting the wake-up/respawn dialogue. Death Sounds and Death Fade Seconds are exported on Wake_Up; an empty bank still fades/respawns safely. DONT. DO. THAT. retains its once-only history and waits until waking ends.

The main door dispatches its close sound from AnimationPlayer.animation_finished only when the finished animation matches Close Animation and the door is closed. Opening still plays its sound at the start, after restoring the world SFX bus.

# F5 debug log and crash diagnostics

Press **F5** from gameplay or a menu to open the log; F5 or Escape closes it and restores the previous pause, mouse and input lock. It shows engine prints, warnings/errors and game breadcrumbs in a scrollable text view. Filter by severity and channel/text, or turn Follow off to inspect older entries. F1 report drafts keep ownership until closed.

Choose **EXPORT LOGS** to write a ZIP, then **OPEN EXPORT FOLDER** to locate it. Console commands `log open`, `log export` and `log folder` offer the same actions. The ZIP includes current and previous session log segments, their session markers, recent engine logs, the in-memory entries, and engine/OS/rendering/scene information. It does not deliberately dump Blackboard, flags or the save file. Authored engine prints are captured as written, so avoid printing secrets.

Logs live in `user://debug_logs/sessions/<timestamp-pid-id>/`; exports default to `user://debug_logs/exports/`. Independent session folders prevent concurrent editor/test instances from overwriting each other. A session without a clean-exit marker is retained for the next export when its process is no longer running. Restart after a crash, then export. An interrupted session can also mean forced termination: this is diagnostic evidence, not a crash dump or a guarantee that the final event survived.

Memory defaults to 2,000 entries. Disk defaults to one 2 MiB active segment plus two rotated segments per session, with eight inactive/active recent session slots and preservation of the selected unexported interrupted session. Engine files are truncated to their latest 8 MiB each when exported. Native callbacks write and flush events under a mutex, never touching UI/SceneTree or recursively printing. The visible view refreshes only while open and when entries change; game diagnostics describe meaningful transitions rather than every physics frame.

# Rail and slider

The Train Rail and Slider are loose store items. They use the existing F pickup, wheel/R rotation, B ghost / B place / F cancel and Q retrieve controls. A rail anchors to any solid surface; a slider only mounts onto a rail and its ghost snaps to the centre of the track. Switch the fan off with E, rotate/rebuild it to reverse, or use two opposing fans for separate controls. A fan built onto a basket on the carriage works too. Ordinary airflow, physical pushes and gravity on a tilted rail also move the carriage. Other built props follow their support as usual.

A resting basket brings its contained objects along, including items dropped into it later. # Blender asset workflow

Create editable, textured 3D assets and show the finished result through actual Blender renders. The user's defaults are realistic environments, textures on every new model, separate room and item assets, and multiple rendered angles at completion. Current explicit art direction takes precedence.

## Start from the project and source

Read the project's instructions, asset guides and relevant source before modelling. Follow any local issue-report workflow, including viewing submitted screenshots. Discover the installed Blender version and available renderer/device; use that installation through scripting or an available Blender connector. Preserve existing source, materials, dimensions and designer transforms when extending a model.

Determine the intended scale, use and art direction from the request and surrounding project. Make routine design choices without stopping for approval. Keep the task's output in its own asset directory and preserve unrelated scene content.

For Remnant-GD, read [references/remnant.md](references/remnant.md). Other projects use their own folders and delivery instructions.

## Model rooms and items separately

- When creating a room, author its shell in its own .blend asset: floor, walls, ceiling, structural openings and architectural trim. Use real window/door openings, plausible thicknesses, human scale and usable clearances.
- Author each distinct item or prop as an independent asset in its own .blend file, with a named collection, local origin/pivot, materials and export. Furniture, machines, movable doors and objects placed inside a room remain reusable independently of the room.
- Assemble the presentation scene with linked assets or collection instances. Keep the room, each prop and the presentation rig in separate named collections. Store item placement on instances; retain each item's local coordinates for reuse.
- Export the room and props separately when exports are part of the task. A combined preview scene is useful alongside those assets. Joining room geometry must not bake loose props into the shell.
- Keep movable subparts separate with useful pivots, such as a door hinge or fan blade centre. A functional or animated part needs more than a visually correct silhouette.

## Finish surfaces and materials

Texture every new model. Finish UVs and a coherent material setup before delivery; avoid untextured grey placeholders. Use scale-correct base colour maps and the normal, roughness or metallic detail needed for the intended surface. Glass, polished metal and other simple surfaces can use deliberate physically based material settings within the finished textured asset.

Use believable proportions, small edge bevels, material variation and restrained wear. Wood grain, tiles, paper print and other directional details must have sensible scale and orientation. Keep imperfections consistent with the environment instead of covering every surface with the same noise.

Preserve supplied textures and material assignments; inspect embedded or nearby image maps before replacing them. Use original maps or appropriately licensed assets and record external sources. Pack textures into native deliverables or provide a complete portable texture directory. A procedural shader must be baked to supported maps when the target export cannot reproduce it.

Read [references/textures-and-export.md](references/textures-and-export.md) for procedural image generation, portable PBR export or game-engine delivery.

## Render and review multiple angles at completion

Use actual renders of the final model. Finish with at least three distinct useful views, typically four for a room: a complete overview or temporary cutaway, two complementary views at human eye height, and a detail/interior view that exposes important materials or geometry. For a prop, show front/three-quarter, opposite/rear, and another angle that reveals its construction. Cover every newly created asset; assembling props into a room does not replace an independent prop view when its shape is obscured.

Set up plausible light sources, appropriate exposure and colour management. Use Cycles for realistic presentation when available, with a supported GPU or CPU fallback. Iterate with quick previews, then render final images at a useful resolution and sufficient samples/denoising. Keep cameras, presentation lights, backdrop and atmospheric effects separate from exported assets.

Open and visually inspect **every final image**. Check framing, hidden or intersecting geometry, mirrored print/UVs, texture scale, missing/black materials, light leaks, noise and excessive haze. Refine observed problems and re-render affected views. Successful command exit or finding an image file does not count as visual review.

Use temporary visibility changes for cutaways and restore the full model. Save the editable source with the intended complete scene, a useful default camera, and matching render aspect. Preserve named cameras so the views can be reproduced. Screenshots or AI concept images cannot stand in for final Blender renders.

## Deliver portable, reviewable assets

Provide the editable native model and its textures, separate files for the room and any props created, requested exports, and the reviewed multi-angle images. Preserve reproducible authoring scripts when used. Summarise scale, asset separation, material setup, verification and relevant limits; distinguish Blender presentation lighting from engine-rendered appearance.

When targeting an engine, verify import, bounds, origins, UVs, materials and movable pivots. Keep presentation-only objects out of exports. Collision, gameplay placement and engine volumetric lighting require their own setup and checks.

Follow the current project's documentation, HTML/Notion summary, build and Git preferences where configured. Preserve publication access and report actual outcomes. # Texture and export checks

## Image maps and UVs

- Set a generated Blender image's colour space, file format and path before assigning its pixel buffer. Changing colour space after writing generated pixels can invalidate that buffer. Save, reload or inspect representative values, and actually view the textured render.
- Base colour uses an appropriate colour space; tangent normal, roughness, metallic and mask maps are non-colour data. Check normal handedness and the target engine's conventions. Keep wood grain, labels and paper text readable from the intended side.
- UV scale should correspond to physical dimensions. Inspect small items independently; a room overview can conceal backwards text, seams or missing surfaces.
- Pack all required image maps into the .blend and verify packed image data. Exported textures must be embedded or supplied with valid portable paths. Keep authoring-only originals outside redundant engine import scans where the project supports it.

## Portable PBR assets

Prefer export-supported Principled materials for base colour, normals, roughness, metallic and transparency. Bake unsupported procedural effects when exporting them. Inspect the exported material assignments and maps rather than assuming the native shader graph survives.

Apply intended scale and evaluate modifiers deliberately. After joining rotated pieces, bake the surviving object's rotation when appropriate: an otherwise correct model can inherit an inflated engine bounding box. Check the actual imported bounds and transforms.

Give each separate prop a useful local pivot and consistent front/up convention. The presentation assembly's world placement belongs on instances. Keep movable parts and their pivots intact; avoid flattening animations or articulated geometry into a room export.

Select only the intended room or prop for each export. Exclude render cameras, light rigs, studio ground and dust volumes. Retain full walls and ceiling even if a preview hides them for a cutaway.

Transparent glass may look different across renderers. A native ray-visibility setting or volumetric rig does not automatically become an engine feature. Verify transparency in the target where needed and state which light-beam/shader effects remain native presentation only. Engine import alone does not establish physics collisions or identical lighting.
