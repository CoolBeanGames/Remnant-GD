Building System (Scripts/Building/)

The test level includes a packed work light beside the player's starting position (1.6, 0.5, -0.5). Pick it up with F and carry the visible crate normally. Press B to hide the crate and show its building ghost, aim at a floor within 8 metres, rotate with the mouse wheel, and press B again to place. Green ghosts are valid; red ghosts are blocked or on an unsupported surface. An invalid second B press leaves placement active so you can adjust and retry. Aim at a placed building within the player's 3 metre interaction range and release Q with empty hands to return it directly to a visible held package in carrying mode. F cancels placement back to visible carrying, keeping the crate in hand. In carrying mode F drops it and right mouse charges/throws it; throw input is suppressed during placement. E remains the ordinary interaction key.

The light is a directional work light, so rotating it changes where it shines. Its base marker snaps to the aimed floor point with a 0.01 metre clearance. Placement accepts the Floor group, rejects slopes above 15 degrees, and checks the light's collision footprint against other bodies, including the player. Ghosts have translucent materials, no gameplay scripts, no collision layers, no audio, and no active lights. They never enter the save registry.

Adding another building

1. Create a scene with a StaticBody3D root using buildable.gd, visible geometry, collision shapes describing its clearance footprint, and an Anchor marker.

2. Create an external buildable_definition .tres, assign its building and generic package scenes, and configure anchor, surface groups, slope, distance, physics mask, local rotation axis, and step.

3. Create an inherited package scene and assign that definition. Place the package in the level.

4. For an optional separate ghost scene, use the same anchor and matching collision footprint. Scripts are stripped before preview nodes enter the tree; gameplay code never runs on ghosts.

5. Add matching wiki/README documentation and a guide log entry.

Carrying and placement modes

Picking up a package only tracks it; the crate stays visible and no ghost is created. The first build action (B press) calls start_building() to create/validate the ghost, save package_original_visible, set package_hidden, and hide the crate. The next B press calls try_build(). Invalid placement retains the hidden crate and ghost for retrying. Drop, throw, changing packages, or controller removal clear the ghost and restore original crate visibility. Q returns a package in visible carrying mode. E does not build.

start_building() returns bool, false on missing references or invalid preview configuration without hiding the crate. package_hidden and package_original_visible track the temporary visibility override.

Imported crate exclusions

Placement rays exclude the player and every held collider supplied by pickup.get_held_collision_rids(). Clearance excludes every held collider while retaining the player. Imported child StaticBody3D colliders are excluded along with the outer RigidBody3D, so a held crate cannot become the light placement surface.

Held-item collision hierarchy

Held items disable collision layers and masks for every CollisionObject3D descendant, including imported nested StaticBody3D bodies and areas. held_collision_state stores each collider and its original layer/mask. Drop, throw and consumption restore these settings and clear the snapshot; freed descendants are skipped. get_held_collision_rids() returns Array[RID] for every live held collider so placement queries can exclude the complete item. This prevents a carried crate from pushing the player or intercepting placement rays.

Grinding and Score

The existing grinding_area Area3D in testing_level.tscn uses Scripts/Level/grinding_area.gd. Its authored volume/position is preserved, monitoring is enabled, and body_entered drives item destruction. It has collision layer 0 and retains its detection mask (default layer 1). Use its collision mask to select additional item physics layers.

Loose rigid-body items are destroyed on entry, including crates whose imported child StaticBody3D collider enters first. Characters and ordinary static scenery are ignored. To remove a wrapper together with its physics body, put the wrapper root in grindable or score. The test-object prefab root is now grindable, so grinding its RigidBody3D also removes its object manager and prompts. A bare RigidBody3D needs no group to be destroyed. The enclosing level/game root is never inferred as an item owner.

Items in the score group increase Blackboard["score"]. An optional child score_object supplies the amount; without one, the amount is 1. A component alone does not make an item score: mark the item's body or logical wrapper root with score. Unmarked items are destroyed without points. The grinder initializes a missing score to 0, preserves an existing numeric total, and adds the amount before queuing deletion. The queued item-root check prevents double scoring across multiple colliders or grinder callbacks before deletion.

ScoreRewards

Autoload

Accelerating score queue with pooled SFX and final batch completion.

Global/score_rewards.gd · Node · UID uid://bs0i77t3jtdef · Autoload ScoreRewards · No custom signals.

Queue timing

enqueue(amount: int) accepts positive item rewards into a shared queue. The first point is immediate. Starting at 0.5 seconds, subtract 0.02 after every award: subsequent waits are 0.48, 0.46, 0.44 seconds and so on. New rewards extend the same accelerated queue. Normal awards add 1 to Blackboard[score] and play loud Score.wav once on pooled global SFX. Zero/negative rewards are ignored.

Once the reduced interval reaches zero or below (floating-point tolerance 0.000001), award all remaining points in one update and play one sound for the batch. Empty queues stop the timer, clear its timestamp guard and reset to the base delay. The next queue begins immediately. Source items/areas may be deleted while queued rewards finish. The timer pauses with the scene tree.

Settings, state and methods

Exports: score_sound: AudioStream (Audio/SFX/Score.wav), score_volume: float = 2.0 (linear, about +6 dB), point_interval: float = 0.5 (base), interval_decrease: float = 0.02. pending_points: int is the remaining count; _current_interval: float stores the decreasing delay; _timer: Timer is one-shot; _next_point_time_usec: int prevents early delivery from bypassing the current delay. _ready() creates/connects the timer. _award_next_point() decreases the delay, awards one or flushes the remainder, plays audio, then schedules or resets. Missing/nonnumeric totals become zero before adding the reward.

Remnant GD Architecture Overview

Godot 4.7

A high-performance modular Godot 4.7 architecture featuring centralized data management, signal-driven flags, dynamic scene/bundle instancing, audio pooling, physical interaction raycasting, and reactive hazard systems.

Engine Version Godot Engine 4.7 Forward+
Physics Engine Jolt Physics (3D)
Graphics API Direct3D 12 (Windows)
Autoload Singletons Blackboard, Flags, SceneManager, Audio, Buildings

Core Architecture Principles

The Remnant-GD codebase is engineered around decoupled, single-responsibility services and components:

  • Decoupled State Management: Systems share references, roots, and runtime objects via the global Blackboard service locator, removing tight dependencies between disparate scene branches.
  • Reactive Flag System: Game states, conditions, and mission progression are observed via Flags and reactive flag resource signals.
  • Dynamic Scene & Bundle Orchestration: Scenes are instanced, attached to parent nodes (or auto-resolved via Blackboard["game_root"]), and grouped into lifecycle bundles through SceneManager.
  • Object Pooling Architecture: High-frequency instances (such as spatial 3D audio players) are pre-allocated and recycled using object_pool (Object_Pool.gd), preventing runtime GC stutter.
  • Decoupled Global Audio: Global spatial and stereo sound playback is dispatched through the Audio autoload (audio_global.gd), automatically acquiring pooled audio_player instances and releasing them on completion.
  • Component-Based Player & Interactivity: The player character is split into isolated controllers: mouse look (player_look_controller.gd), kinematic WASD movement with sprint cadence (player_move_controller.gd), group-filtered targeting (raycaster.gd), and interaction dispatch (player_interact.gd).
  • Proxy Interaction Pattern: Physical colliders forward player interactions up to logic nodes via interact_pass_through.gd, keeping collision shapes modular.
  • Contextual Physics Audio: Physics props (e.g., test_object.tscn) evaluate collision partners using collision_sound_matrix.gd and data-driven collision_sound_entry resources to trigger material-appropriate sounds.
💡 Autoload Singleton Registration

Active autoload singletons in project.godot are mapped directly to canonical scripts in Global/ via engine UIDs: Blackboard, Flags, SceneManager, and Audio.

Execution Logic

Every frame during _process(), it checks for Input.is_action_just_released("confirm") (the E key):

res://Scripts/Player/player_interact.gd
func _process(delta: float) -> void:
    if Input.is_action_just_released("confirm"):
        if ray.is_looking_at_something():
            var target: Node3D = ray.get_looked_at()
            if target.has_method("interact"):
                target.interact()

Raycast debugging is disabled in player.tscn. Target groups include look-prompt; object_prompts components register their owner in this group to support prompt-only objects.

The player scene configures interact, pick-up and building as target groups, supporting both package pickup and Q unbuilding through the existing ancestor search.
